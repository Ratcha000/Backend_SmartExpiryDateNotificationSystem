
### 3.0) Ingredients API Specification

เส้น `Ingredients` เป็นแกนหลักของ inventory และ expiry tracking โดย v1 ให้ถือว่า 1 ingredient record คือ 1 รายการสต็อกที่มีหน่วยชัดเจนและมี quantity คงเหลือปัจจุบัน

หลักการของข้อมูล
- `initialQuantity` คือปริมาณตอนสร้างรายการ
- `quantity` คือปริมาณคงเหลือปัจจุบัน
- `unit` คือหน่วย canonical ของรายการนั้น เช่น `kg`, `g`, `pcs`, `bottle`, `pack`, `liter`
- `status=used` ควรเกิดอัตโนมัติเมื่อ quantity ลดเหลือ `0`
- ถ้ามีการใช้วัตถุดิบบางส่วน ต้องบันทึก `UsageHistory` แบบ `consumed`

ตัวอย่าง `IngredientResponse`

```json
{
  "id": "ingredient-id",
  "restaurantId": "restaurant-id",
  "name": "Pork loin",
  "category": "meat",
  "initialQuantity": 12.0,
  "quantity": 7.5,
  "unit": "kg",
  "expiryDate": "2026-07-28",
  "notifyDaysBefore": 2,
  "status": "active",
  "daysLeft": 6,
  "isExpiring": false,
  "isExpired": false,
  "scannedBy": "user-id",
  "scannedAt": "2026-07-22T10:15:00Z",
  "lastUsedAt": "2026-07-22T12:30:00Z",
  "updatedBy": "user-id",
  "createdAt": "2026-07-22T10:15:00Z",
  "updatedAt": "2026-07-22T12:30:00Z"
}
```

ตัวอย่าง unit ที่ควรใช้ใน v1
- เนื้อสัตว์: `kg`, `g`
- เครื่องปรุงขวด: `bottle`
- ของนับชิ้น: `pcs`
- ของแบบแพ็ก: `pack`
- ของเหลว: `liter`, `ml`

#### 3.0.1) POST /api/ingredients

หน้าที่
- สร้าง ingredient ใหม่ในร้าน
- รองรับทั้งการกรอก manual และข้อมูลที่มาจาก OCR แล้วผู้ใช้ตรวจแก้ก่อน save

Auth
- `Manager, Employee`

request body

```json
{
  "restaurantId": "restaurant-id",
  "name": "Pork loin",
  "category": "meat",
  "initialQuantity": 12.0,
  "quantity": 12.0,
  "unit": "kg",
  "expiryDate": "2026-07-28",
  "notifyDaysBefore": 2,
  "scannedBy": "user-id",
  "scannedAt": "2026-07-22T10:15:00Z"
}
```

validation
- `restaurantId` ต้องเป็นร้านที่ user มีสิทธิ์เข้าถึง
- `name` ห้ามว่าง
- `category` ห้ามว่าง
- `initialQuantity` ต้องมากกว่า `0`
- `quantity` ต้องมากกว่าหรือเท่ากับ `0`
- `initialQuantity >= quantity`
- `unit` ห้ามว่าง
- `expiryDate` ต้อง parse ได้
- `notifyDaysBefore >= 0`

behavior
- ถ้า `quantity = 0` ตอนสร้าง ให้ระบบพิจารณา reject request สำหรับ v1 เพื่อกันข้อมูลไม่สมเหตุผล
- สร้าง usage history แรกเป็น `added`
- ตั้ง `status=active` โดย default ถ้ายังไม่หมดอายุ

success response
- HTTP `201 Created`
- คืน `IngredientResponse`

#### 3.0.2) GET /api/ingredients?restaurantId=&status=&category=

หน้าที่
- ดึงรายการวัตถุดิบของร้าน
- ใช้สำหรับหน้า ingredient list, dashboard, filter by status/category

Auth
- `Manager, Employee`

query params
- `restaurantId` required
- `status` optional เช่น `active`, `used`, `deleted`, `expired`
- `category` optional

behavior
- ควร sort default ตาม `expiryDate` ใกล้สุดก่อน
- response ควรมี `quantity`, `unit`, `daysLeft`, `isExpiring`, `isExpired`

success response
- HTTP `200 OK`
- คืน array ของ `IngredientResponse`

#### 3.0.3) GET /api/ingredients/{id}

หน้าที่
- ดึงรายละเอียด ingredient รายชิ้น

Auth
- `Manager, Employee`

behavior
- ต้องตรวจว่า ingredient นั้นอยู่ใน `restaurantId` ที่ user เข้าถึงได้

success response
- HTTP `200 OK`
- คืน `IngredientResponse`

#### 3.0.4) PUT /api/ingredients/{id}

หน้าที่
- แก้ไขข้อมูลหลักของ ingredient

Auth
- `Manager, Employee`

request body

```json
{
  "name": "Pork loin",
  "category": "meat",
  "initialQuantity": 12.0,
  "quantity": 9.0,
  "unit": "kg",
  "expiryDate": "2026-07-29",
  "notifyDaysBefore": 3
}
```

validation
- ใช้ validation เดียวกับ create เท่าที่เกี่ยวข้อง
- ถ้าแก้ `quantity` ผ่าน endpoint นี้ ต้องยังคงบันทึก usage history เป็น `edited`
- ถ้าต้องการแก้ quantity แบบมีเหตุผลเชิง stock movement ให้ใช้ `/consume`, `/restock`, `/adjust-quantity` เป็นหลัก

behavior
- อัปเดต `updatedAt`, `updatedBy`
- ถ้า quantity ลดเหลือ `0` จากการแก้ไข ให้เปลี่ยน `status=used`

success response
- HTTP `200 OK`
- คืน `IngredientResponse`

#### 3.0.5) PATCH /api/ingredients/{id}/consume

หน้าที่
- หักปริมาณวัตถุดิบเมื่อมีการนำไปใช้บางส่วน

Auth
- `Manager, Employee`

request body

```json
{
  "quantity": 2.5,
  "note": "Used for lunch prep"
}
```

validation
- `quantity` ต้องมากกว่า `0`
- `quantity` ต้องไม่เกิน quantity คงเหลือของ ingredient

behavior
- หัก quantity คงเหลือ
- ตั้ง `lastUsedAt`
- ถ้า quantity เหลือ `0` ให้ mark `status=used` อัตโนมัติ
- สร้าง usage history เป็น `consumed` พร้อม `quantityBefore`, `quantityChanged`, `quantityAfter`, `unit`

success response
- HTTP `200 OK`
- คืน `IngredientResponse`

error cases
- `400 Bad Request` ถ้า quantity ที่ขอใช้ไม่ถูกต้อง
- `409 Conflict` ถ้า stock ไม่พอและเลือกใช้ semantic status code แยกกรณี

#### 3.0.6) PATCH /api/ingredients/{id}/restock

หน้าที่
- เพิ่ม quantity ให้ ingredient เดิมเมื่อมีการเติมของเพิ่มในรายการเดิม

Auth
- `Manager, Employee`

request body

```json
{
  "quantity": 3.0,
  "note": "Added from same batch"
}
```

validation
- `quantity` ต้องมากกว่า `0`

behavior
- เพิ่ม quantity คงเหลือ
- อัปเดต `updatedAt`, `updatedBy`
- ถ้ารายการเดิมเป็น `used` แต่มีการเติมของกลับมา ให้ระบบเปลี่ยน `status` กลับเป็น `active`
- สร้าง usage history เป็น `restocked`

success response
- HTTP `200 OK`
- คืน `IngredientResponse`

หมายเหตุ
- ถ้าเติมของเป็นคนละล็อตและ expiryDate ต่างกันมาก ควรพิจารณาสร้าง ingredient ใหม่แทนในอนาคต

#### 3.0.7) PATCH /api/ingredients/{id}/adjust-quantity

หน้าที่
- ปรับ quantity โดยตรงจากการตรวจนับของจริงหรือแก้ข้อมูลผิดพลาด

Auth
- `Manager`

request body

```json
{
  "quantity": 8.0,
  "reason": "Physical stock count correction"
}
```

validation
- `quantity` ต้องมากกว่าหรือเท่ากับ `0`
- `reason` ควรบังคับสำหรับ audit trail

behavior
- set quantity ใหม่ตรง ๆ
- ถ้า quantity เป็น `0` ให้เปลี่ยน `status=used`
- ถ้า quantity มากกว่า `0` และสถานะเดิมเป็น `used` ให้สามารถกลับเป็น `active` ได้
- สร้าง usage history เป็น `adjusted`

success response
- HTTP `200 OK`
- คืน `IngredientResponse`

#### 3.0.8) PATCH /api/ingredients/{id}/used

หน้าที่
- ปิดรายการวัตถุดิบเป็น `used` แบบ explicit

Auth
- `Manager, Employee`

request body

```json
{
  "note": "Marked used manually"
}
```

behavior
- ใช้ในกรณี manual close-out หรือ fallback flow
- สำหรับ v1 อาจเลือก set `quantity=0` ไปพร้อมกัน เพื่อให้ข้อมูลไม่ขัดกัน
- สร้าง usage history เป็น `used`

success response
- HTTP `200 OK`
- คืน `IngredientResponse`

#### 3.0.9) PATCH /api/ingredients/{id}/delete

หน้าที่
- soft delete ingredient ออกจากมุมมองใช้งานปกติ

Auth
- `Manager, Employee`

request body

```json
{
  "note": "Removed duplicate entry"
}
```

behavior
- เปลี่ยน `status=deleted`
- ไม่ควรลบข้อมูลจริงออกจากฐานข้อมูลใน v1
- สร้าง usage history เป็น `deleted`

success response
- HTTP `200 OK`
- คืน `IngredientResponse`

#### 3.0.10) PATCH /api/ingredients/{id}/status

หน้าที่
- ปรับสถานะ ingredient แบบ generic สำหรับ workflow พิเศษ

Auth
- `Manager, Employee`

request body

```json
{
  "status": "expired",
  "note": "Manual override"
}
```

validation
- รับเฉพาะค่าที่อยู่ใน enum ที่ระบบรองรับ

behavior
- ควรใช้ endpoint นี้เฉพาะกรณีที่ endpoint เฉพาะทางไม่ครอบคลุม
- ถ้า status ใหม่ขัดกับ quantity เช่น `active` แต่ quantity = `0` backend ควร reject หรือ normalize ให้ consistent

success response
- HTTP `200 OK`
- คืน `IngredientResponse`

#### 3.0.11) GET /api/ingredients/expiring?restaurantId=

หน้าที่
- ดึงรายการวัตถุดิบที่ใกล้หมดอายุตามกติกา `daysLeft <= notifyDaysBefore`

Auth
- `Manager, Employee`

query params
- `restaurantId` required

behavior
- ควรคืนเฉพาะ `status=active`

success response
- HTTP `200 OK`
- คืน array ของ `IngredientResponse`

#### 3.0.12) GET /api/ingredients/expired?restaurantId=

หน้าที่
- ดึงรายการวัตถุดิบที่หมดอายุแล้ว

Auth
- `Manager, Employee`

query params
- `restaurantId` required

behavior
- backend สามารถ derive จาก `daysLeft < 0` หรือ status ที่ sync แล้วก็ได้ แต่ response ต้อง consistent

success response
- HTTP `200 OK`
- คืน array ของ `IngredientResponse`

#### 3.0.13) GET /api/ingredients/low-stock?restaurantId=

หน้าที่
- ดึงรายการวัตถุดิบที่ quantity คงเหลือต่ำ เพื่อช่วยวางแผนซื้อ

Auth
- `Manager, Employee`

query params
- `restaurantId` required
- `category` optional

behavior
- v1 สามารถใช้ heuristic จาก quantity ปัจจุบัน + purchase recommendation engine
- ถ้ายังไม่มี par level ต่อ ingredient ให้ endpoint นี้ใช้เกณฑ์ภายในระบบหรือค่าที่ derive จาก usage history ได้

success response
- HTTP `200 OK`
- คืน array ของ `IngredientResponse` หรือ shape ที่มี low-stock reason เพิ่มเติม

ข้อเสนอสำหรับ error response ของ Ingredients

```json
{
  "timestamp": "2026-07-22T14:00:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Consume quantity cannot exceed remaining quantity"
}
```
